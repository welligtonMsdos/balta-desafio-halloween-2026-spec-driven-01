# Tarefas — Autenticação e CRUD de Usuários

|---|---|---|---|---|
| T-01 | Alinhar a especificação, o plano e a constituição ao CRUD completo de usuários **(concluída)** | Solicitação do usuário | — | `spec.md`, `plan.md` e `constitution.md` descrevem consulta, listagem, atualização e exclusão de usuários, inclusive regras de autenticação, titularidade e validação de e-mail e senha para alterações. |
| T-02 | Criar a solution .NET 10 e os projetos `Auth.Api`, `Auth.Application`, `Auth.Domain`, `Auth.Infrastructure`, `Auth.UnitTests` e `Auth.IntegrationTests` | Plano — Arquitetura | T-01 | A solution compila, respeita a separação API → Application/Infrastructure → Domain e possui pastas próprias para serviços e repositórios. |
| T-03 | Configurar dependências, análise de código, nullable reference types e a configuração base da aplicação | Plano — Decisões | T-02 | O build é reprodutível, falha para avisos tratados como erro quando configurado e não há segredos versionados. |
| T-04 | Definir convenções de erros HTTP e o tratamento global de exceções | Plano — Contratos | T-02 | Erros de validação, conflito, não encontrado, não autorizado e falhas inesperadas retornam respostas JSON consistentes, sem dados sensíveis. |
| T-05 | Implementar entidade `User` e seus invariantes de domínio | Plano — Modelo de dados | T-02 | A entidade possui identificador, e-mail, e-mail normalizado, hash de senha e data UTC de criação, sem expor senha em texto puro. |
| T-06 | Implementar normalização e validação de e-mail | Plano — Decisões | T-05 | Espaços externos são removidos, o e-mail é normalizado em minúsculas invariantes e e-mails ausentes ou inválidos são rejeitados. |
| T-07 | Implementar política de senha forte | Spec — RN-03 a RN-08 | T-05 | A validação exige ao menos 10 caracteres, maiúscula, minúscula, número e caractere especial, informando todos os requisitos não atendidos. |
| T-08 | Criar contratos de Repository Pattern e de serviços da aplicação | Plano — Arquitetura | T-05, T-06, T-07 | Existem interfaces de repositório para usuários e contratos para hash/verificação de senha, relógio e token; serviços de aplicação dependem apenas dessas abstrações, nunca de HTTP, `DbContext` ou EF Core. |
| T-09 | Implementar `UserService` para cadastro de usuário | Spec — RF-01 a RF-07 | T-08 | O serviço usa o repositório por interface, cria conta somente para e-mail único e dados válidos, aplica hash à senha e retorna apenas id e e-mail. |
| T-10 | Implementar `UserService` para consulta de usuário por identificador | CRUD | T-08 | O serviço usa o repositório por interface e retorna os dados públicos do usuário solicitado, nunca `password_hash` ou senha. |
| T-11 | Implementar `UserService` para listagem de usuários | CRUD | T-08 | O serviço usa o repositório por interface, retorna usuários com campos públicos e suporta paginação com limites validados. |
| T-12 | Implementar `UserService` para atualização de usuário | CRUD | T-08 | O serviço usa o repositório por interface, permite alterar e-mail e/ou senha, revalida os campos, impede e-mail duplicado e recalcula o hash quando a senha muda. |
| T-13 | Implementar `UserService` para exclusão de usuário | CRUD | T-08 | O serviço usa o repositório por interface, remove o usuário solicitado e retorna resultado adequado para usuário inexistente. |
| T-14 | Implementar abstrações de senha com `PasswordHasher<TUser>` | Plano — Decisões | T-08 | Senhas são geradas e verificadas com hash e salt; nenhum log, contrato ou entidade pública contém senha em texto puro. |
| T-15 | Implementar serviço de emissão de JWT | Plano — Decisões | T-08 | O token assinado inclui `sub`, `email`, `iss`, `aud`, `iat` e `exp`, usando chave e duração vindas de configuração. |
| T-16 | Implementar `AuthService` para login | Spec — RF-08 a RF-11 | T-08, T-14, T-15 | O serviço usa o repositório e os serviços de senha/token por abstração; credenciais corretas produzem JWT e e-mail inexistente ou senha incorreta têm a mesma resposta de falha. |
| T-17 | Criar `DbContext`, mapeamento EF Core e implementação PostgreSQL do `IUserRepository` | Plano — Arquitetura e Modelo de dados | T-05, T-08 | A implementação do repositório persiste e consulta usuários com os campos e contratos definidos no domínio; `DbContext` não é acessado fora da infraestrutura. |
| T-18 | Criar migração inicial e restrições de integridade do PostgreSQL | Plano — Modelo de dados | T-17 | A migração cria `users`, chave primária UUID, `NOT NULL` e índice único `ux_users_normalized_email` em `normalized_email`. |
| T-19 | Traduzir violação da unicidade do banco em conflito de negócio | Plano — Riscos | T-09, T-17, T-18 | Cadastros ou atualizações concorrentes com o mesmo e-mail resultam em uma única conta e resposta `409 Conflict` para a outra operação. |
| T-20 | Configurar autenticação e autorização JWT Bearer na API | Plano — Decisões | T-15 | A API valida assinatura, emissor, audiência e expiração; chave ausente ou insegura impede a inicialização. |
| T-21 | Criar endpoint `POST /auth/register` | Plano — Contratos | T-04, T-09, T-19 | Retorna `201 Created` para cadastro válido, `400 Bad Request` para dados inválidos e `409 Conflict` para e-mail em uso. |
| T-22 | Criar endpoint `POST /auth/login` | Plano — Contratos | T-04, T-16, T-20 | Retorna `200 OK` com `accessToken`, `tokenType` e `expiresIn` para credenciais válidas; falhas retornam somente `401 Unauthorized` genérico. |
| T-23 | Definir regra de autorização do CRUD | CRUD e autenticação | T-01, T-20 | O plano define e a API aplica que um usuário autenticado só pode consultar, atualizar e excluir a própria conta; a listagem é permitida a usuários autenticados e retorna somente dados públicos. |
| T-24 | Criar endpoint `GET /users/{id}` autenticado | CRUD | T-04, T-10, T-20, T-23 | O endpoint retorna `200 OK` com dados públicos apenas para o titular do `sub`; ausência retorna `404` e tentativa de outro usuário retorna `403`. |
| T-25 | Criar endpoint `GET /users` autenticado | CRUD | T-04, T-11, T-20, T-23 | O endpoint permite a usuários autenticados listar dados públicos de usuários, pagina resultados e nunca retorna dados de senha. |
| T-26 | Criar endpoint `PUT /users/{id}` autenticado | CRUD | T-04, T-12, T-19, T-20, T-23 | Atualiza e-mail e/ou senha do titular, retorna dados públicos e respeita `400`, `403`, `404` e `409` conforme o caso. |
| T-27 | Criar endpoint `DELETE /users/{id}` autenticado | CRUD | T-04, T-13, T-20, T-23 | Exclui somente a própria conta, retorna `204 No Content`, devolve `404` para id inexistente e `403` para acesso de terceiro. |
| T-28 | Impedir vazamento de credenciais em logs e respostas | Spec — RN-09 e RN-10 | T-14, T-21, T-22, T-24, T-25, T-26, T-27 | Logs, erros e payloads são revisados; senha e hash não aparecem e falhas de login não revelam existência do e-mail. |
| T-29 | Criar testes unitários de domínio e aplicação | Plano — Testes | T-06 a T-16 | Cobrem normalização de e-mail, todos os critérios de senha, cadastro, conflito, login válido/inválido, geração de token e operações CRUD com substitutos. |
| T-30 | Criar testes unitários de autorização de proprietário | CRUD e autenticação | T-23 a T-27 | Cobrem o vínculo entre o `sub` do JWT e o id de rota, incluindo tentativa de acesso por outro usuário. |
| T-31 | Criar Dockerfile multiestágio da API | Plano — Decisões | T-02, T-21 a T-27 | A imagem compila e executa a API como usuário não privilegiado, sem segredos embutidos. |
| T-32 | Criar `docker-compose.yml` para API e PostgreSQL efêmero | Plano — Contexto e Modelo de dados | T-18, T-31 | `docker compose up --build` inicia os serviços; PostgreSQL usa `tmpfs` em `/var/lib/postgresql/data`, não declara volume persistente e possui healthcheck. |
| T-33 | Configurar migração automática controlada no ambiente Docker | Plano — Decisões | T-18, T-32 | Em um banco novo, o schema é aplicado antes de a API aceitar requisições; falhas de migração encerram a inicialização de modo visível. |
| T-34 | Criar contêiner e Compose exclusivos para testes | Plano — Testes e operação em Docker | T-29, T-31, T-32 | `docker-compose.test.yml` executa `dotnet test`, inicia PostgreSQL em `tmpfs`, aguarda saúde do banco e encerra com o código de saída da suíte. |
| T-35 | Criar testes de integração de cadastro e login | Spec — Critérios de aceite | T-21, T-22, T-33, T-34 | Validam `201`, e-mail duplicado inclusive com capitalização diferente, regras de senha, `200` com JWT e `401` genérico para credenciais inválidas. |
| T-36 | Criar testes de integração do CRUD e autorização | CRUD e autenticação | T-24 a T-27, T-33, T-34 | Validam criar, consultar, listar conforme política, atualizar, excluir, erros de id inexistente, acesso de terceiro, duplicidade e ausência de senha/hash nas respostas. |
| T-37 | Validar configuração JWT e o conteúdo do token em integração | Plano — Decisões | T-20, T-22, T-34 | O teste valida assinatura, emissor, audiência, expiração e claims exigidas; token expirado ou adulterado é rejeitado. |
